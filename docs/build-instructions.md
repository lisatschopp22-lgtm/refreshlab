# Build instructions: refreshLab local prototype

You are building a working, locally runnable prototype of **refreshLab**, a
marketplace for used laboratory equipment. Read this file completely before
writing code. Then read `docs/execution-plan.md` (requirements review,
architecture decisions, data model, phase details) and open
`docs/mockups/refreshlab-20-mockups.html` in a browser (it has a screen
switcher with 20 screens; the design references below refer to its screen
numbers). `CLAUDE.md` in the repo root holds the standing conventions.

## 1. Mission and success criteria

Deliver a prototype that a product owner can use to test **designs, flows and
behaviours** with realistic data, not a mock-up. It runs entirely on a
developer laptop. It will be refactored later, so do not build anything that
only matters for hosting, CI/CD, monitoring or scale.

Done means all of the following are true on a fresh clone:

1. `npm install && npx supabase start && npm run db:reset && npm run dev`
   brings up the site with seeded content in German and English.
2. The five journeys below pass as Playwright tests and can be done by hand
   with the seeded personas.
3. `npm run check` passes.
4. Every screen can be viewed in at least three colour palettes without
   any code change (see §4).
5. `README.md` explains setup, personas, flags, palettes and scripts in
   under one page.

The five journeys:

| # | Journey | Persona |
|---|---------|---------|
| J1 | Search → filter by facets → open a listing → see JSON-LD in page source | anonymous |
| J2 | Register → create an organisation → publish a listing with images → find it in search | new user |
| J3 | Ask the seller from a listing → seller replies → buyer sees unread badge → report a message | buyer + seller |
| J4 | Make an offer → seller counters → buyer accepts → pay with the fake provider → seller marks shipped → buyer confirms receipt → payout released → both see invoices | buyer + seller |
| J5 | Admin edits another user's listing, hides a comment, resolves a report, suspends a user, edits the FAQ page → each action appears in the audit log | admin |

## 2. Fixed decisions (do not re-open)

| Area | Decision |
|------|----------|

| Sale modes | fixed price, make-an-offer, or both. **No auctions.** |

## 3. Design brief

The mockups are the design reference, but read them as follows:

- **Colour is not decided.** The mockups are green because that was the first
  idea. Build the UI colour-agnostic: one brand hue variable and derived
  tokens (OKLCH), plus neutral greys. Ship three palettes and a runtime
  switcher (§4). Green is one of the three, not the default in code.
- **Typography and density are decided by the mockups**: a clean sans (use
  Inter via `next/font`, with IBM Plex Sans as a second option in the theme
  switcher), monospace for identifiers (record IDs, serial numbers, prices in
  tables), generous white space on public pages, denser tables in account and
  admin areas.
- **Tone**: clean, academic, usable first. Humour lives in copy only (empty
  states, success messages, hero kicker), never in controls. Keep the humorous
  strings in the message files under a `humour.*` namespace so they can be
  swapped or removed.
- **Trust signals are first-class UI**: verified badge, condition grade,
  location, response time, "inspected" and "warranty" chips appear on cards
  and detail pages the same way everywhere. Build them once as components.

## 4. Palette and theme mechanics (Phase 0, non-negotiable)

`src/ui/tokens.css`:

```css
:root {
  --hue: 150;            /* brand hue, overridden per palette */
  --chroma: 0.14;
  --brand-50:  oklch(0.97 calc(var(--chroma) * 0.2) var(--hue));
  --brand-500: oklch(0.55 var(--chroma) var(--hue));
  --brand-700: oklch(0.42 var(--chroma) var(--hue));
  /* semantic tokens used by components */
  --bg, --bg-subtle, --fg, --fg-muted, --border, --primary, --primary-fg,
  --accent, --success, --warning, --danger, --ring, --radius-*, --shadow-*
}
:root[data-palette="botanical"] { --hue: 150; ... }
:root[data-palette="clinical"]  { --hue: 230; --chroma: 0.08; ... }
:root[data-palette="ember"]     { --hue: 40;  ... }
:root[data-theme="dark"] { ...dark values for the semantic tokens... }
```

- Tailwind v4 `@theme` maps utility colours to these tokens (`bg-primary`,
  `text-fg-muted` …). Lint rule or grep in `npm run check` fails on
  `bg-(red|green|blue|…)-\d+` and on hex colours in `src/` outside `tokens.css`.
- Switcher: `?palette=` and `?theme=` query params set a cookie; a small
  floating control (dev only) exposes palette, theme, font and density. The
  `/design` route shows every component and a sample of each page section.
- Data-viz colours (if any) also derive from the tokens.

## 5. Working method

- Work **phase by phase** in the order below. Finish a phase, run
  `npm run check` and the phase's Playwright test, verify in the browser,
  commit with `phase N: …`, then continue. Never start Phase N+1 with Phase N
  red.
- Do not ask questions. Every open point has a default in
  `docs/execution-plan.md` §1.3 and §9. If you must choose something not
  covered, choose the simplest option that keeps the behaviour testable,
  write it down in `docs/decisions.md` (one line: date, decision, why), and
  where reasonable put it behind a flag in `src/domain/flags.ts`.
- Build vertically: schema → domain function → server action → UI, feature by
  feature. Do not generate the whole schema first and the whole UI last.
- Seed data is part of the product. Realistic manufacturers, models with
  real spec keys, plausible CHF prices, Swiss/EU cities, German copy. Use a
  deterministic seed (fixed RNG) so screenshots are reproducible.
- Every list has an empty state, every form has validation with messages,
  every mutation has a loading and error state. Use `zod` schemas shared
  between server actions and forms.
- Prefer Server Components; use client components only for interaction.
- Keep the code plain. No abstractions for one call site. No repository
  layer over Drizzle. No event bus beyond the outbox table.
- Do not install a UI kit as a dependency; copy the handful of primitives you
  need into `src/ui` so the tokens control everything.
- After each phase, append a short entry to `docs/progress.md`: what works,
  what was skipped, how to try it.

## 6. Phases

Detailed task lists are in `docs/execution-plan.md` §5. Summary with
acceptance criteria:

### Phase 0 – Foundation
Next.js app, Supabase local, Drizzle schema for all tables in
`execution-plan.md` §4, migrations, seed (12 categories, 15 manufacturers,
~60 models, ~150 listings, 20 users incl. 2 admins and 3 organisations,
comments, conversations, offers, orders in every state, 6 content pages),
next-intl, tokens + palettes + `/design`, primitives, scripts, Vitest and
Playwright smoke tests, README.
**Accept:** fresh clone runs; `/design` shows all primitives in 3 palettes × 2 themes.

Personas to seed (password `refreshlab` for all):
`admin@refreshlab.local`, `anna.buyer@refreshlab.local`,
`beat.seller@refreshlab.local` (private seller),
`dealer@biorefurb.local` (owner of org "BioRefurb GmbH"),
`lab@lifescience-basel.local` (owner of org "LifeScience Basel AG").

### Phase 1 – Public catalogue and search
Home, categories, manufacturers, model pages, listing pages, search with
facets, SEO (metadata, canonical, OG, JSON-LD `Product`/`Offer`/
`Organization`/`BreadcrumbList`), `sitemap.xml`, `robots.txt`, `/api/feed/listings`.
**Accept:** J1 passes; `curl` of a listing page contains price, condition and
JSON-LD; facet counts are correct against the DB.

### Phase 2 – Accounts, organisations, selling
Sign-up/in/out, magic link and reset via Mailpit, profile settings with
avatar, organisations and members, dashboard, create-listing wizard with
model typeahead and "propose new model", images and attachments upload,
edit, status changes, soft delete, watchlist, saved searches, public
profile/organisation pages.
**Accept:** J2 passes; a proposed model appears in the admin queue (Phase 5
reads it; for now it is just a row with `status = pending`).

### Phase 3 – Comments and messages
Threaded comments on model and listing pages with edit/delete/report;
conversations from a listing, inbox, unread counts, attachments, block,
report; polling every 5 s; notification email via outbox to Mailpit.
**Accept:** J3 passes in two browser contexts.

### Phase 4 – Offers, orders, payments
Offer state machine, buy-now, order state machine with fee, milestone order
page, `PaymentProvider` with `FakeProvider` (local checkout page with
Pay/Fail and a simulated bank transfer that admin marks received), invoices
(HTML), disputes, payout release on receipt confirmation. `StripeProvider`
last, only if keys are present; the suite must pass without keys.
**Accept:** J4 passes on `FakeProvider`; unit tests cover every state
transition and the fee cap.

### Phase 5 – Admin
`/admin` with KPI strip; users, organisations, listings, models (approve
proposals, merge duplicates), comments, orders/disputes, reports queue,
content pages (Markdown per locale, publish toggle, rendered at
`/[locale]/p/[slug]`), settings (fee rule, categories, spec schemas), audit
log viewer. Dark palette is the default there via `data-palette` on the
admin layout, but it must work in every palette.
**Accept:** J5 passes; every admin mutation has an `audit_log` row.

### Phase 6 – Test harness and experiments
All five journeys as Playwright tests; screenshot suite of key pages ×
palettes; flags (`offersEnabled`, `requireListingReview`,
`commentsOnListings`, `showPriceRangeOnModel`, `buyNowEnabled`) wired into UI
and admin settings; `npm run db:seed -- --listings 5000` for volume;
`docs/decisions.md` complete.
**Accept:** `npm run check && npm run e2e` green; README lists flags and
palettes.

### Phase 7 – Optional (only if all above is green)
Typesense behind `SearchProvider`; Supabase Realtime for messages; CSV
listing import (S7); price history block from completed orders.

## 7. Quality bar

- TypeScript strict, no `any` outside integration adapters.
- Lighthouse (local, desktop) on home, search and listing: Performance ≥ 80,
  SEO ≥ 95, Accessibility ≥ 90. Fix what the report says before moving on.
- Keyboard-navigable forms and dialogs; visible focus ring from tokens.
- Mobile layouts for all public pages and the account area at 375 px.
- No console errors in the browser on any seeded page.
